# P1 — 架构升级：继承 NetworkRoomManager / NetworkRoomPlayer（历史方案，已废止）

> 本章保留用于记录最初的架构判断。由于 `NetworkRoomManager` 的全局场景切换不适合单端口多房间，实际运行方案已改为 `SocketRoomManager : NetworkManager + RoomRegistry + MatchInterestManagement`，后续任务以 M2、M3-S、M2-V 和 P4-P6 为准。

## 1.1 三个关键事实（决定整个方案）

1. **官方 Room 例子是"双 prefab + ReplacePlayerForConnection"**：`roomPlayerPrefab`（NetworkIdentity + NetworkRoomPlayerExt，房间元数据）+ `playerPrefab`（游戏玩家，含移动/NetworkTransform/视觉），靠 `NetworkServer.ReplacePlayerForConnection` 在进 GameplayScene 时替换。**不是**"一个 NetworkIdentity 同时挂 NetworkRoomPlayer + 游戏组件"。
2. **当前手写实现是"晚加入式重进"而非"玩家替换"**：`SocketNetworkManager.OnServerAddPlayer`（:87-105）在每个场景都 `AddPlayerForConnection`，切场景后旧 `NetworkPlayer` 随场景销毁、客户端重新 Ready/AddPlayer——所以"能玩"，但 netId/displayName/leader 全重置、状态机有竞态。这正是 P1 要根治的。
3. **生成资产是陈旧的**（同 P0 根因）：`Player.prefab` 里 `NetworkPlayer` 带四个旧 sync 字段（`Player.prefab:152-155`）、`config`/`characterController` 空引用、`NetworkTransformUnreliable` 是 `syncDirection: ClientToServer`。**当前 demo 的服务器权威移动实际是死的**（`NetworkPlayer.FixedUpdate` 第一行 `if (!isServer || config == null) return`）。

## 1.2 NetworkRoomManager 生命周期全景（可覆写面）

**红线：以下 8 个入口已被基类做成"房间"语义并在末尾调 `OnRoom*` 钩子，子类一律不得 override（否则房间逻辑整体失效）**：`OnServerAddPlayer / OnServerReady / OnServerConnect / OnServerDisconnect / OnClientSceneChanged / ServerChangeScene / OnServerSceneChanged / OnStartServer`。

子类只能碰两个层面：

- **`SocketRoomManager : NetworkRoomManager` 覆写的 `OnRoom*`**：

| 虚方法 | 语义 | 本项目用途 |
|---|---|---|
| `OnRoomStartServer` / `OnRoomStopServer` | 服务端启停 | EnsureRoomState/EnsureRoomChat（DDOL） |
| `OnRoomServerConnect` / `OnRoomServerDisconnect` | 连接/断开（disconnect 时 roomSlots 已清好、ready 已复位） | `allowLateJoiners` 拦截 / Leader 转移 |
| `OnRoomServerCreateRoomPlayer` | 自定义房间玩家创建（默认 null→roomPlayerPrefab） | 可选 |
| `OnRoomServerCreateGamePlayer` | 自定义游戏玩家创建（默认 playerPrefab+GetStartPosition） | 迁入手写 startPos/fallback 间距逻辑 |
| `OnRoomServerSceneLoadedForPlayer` | 房间→游戏玩家替换前做数据搬运；返回 false 中止 | 拷贝 displayName/displayColor/isLeader |
| `OnRoomServerSceneChanged` | 每次切场景完成（pending 已排空之后） | 交互物重置 / phase 派生 |
| `OnRoomServerPlayersReady` / `NotReady` | 全员就绪翻转 | `autoStartWhenAllReady` 判定 |
| `OnRoomClientSceneChanged` / `OnRoomClientEnter` / `OnRoomClientExit` | 客户端侧 | UI 刷新 |

- **`SocketRoomPlayer : NetworkRoomPlayer` 覆写**：`Start`、`OnClientEnterRoom`、`OnClientExitRoom`、`ReadyStateChanged`、`IndexChanged`。

**关键机制**：
- **`roomSlots`**：不是服务端手动加，而是每个 `NetworkRoomPlayer.Start` 自己 `room.roomSlots.Add(this)`（`NetworkRoomPlayer.cs:54`），服务端/客户端各自维护一份。手写 `FindObjectsByType<NetworkPlayer>` 是等价但更脆的写法。
- **`pendingPlayers` 竞态**（官方解法）：RoomScene 加人 → `SceneLoadedForPlayer` 进 pending；全 ready → `ServerChangeScene(GameplayScene)` → 先 `SetAllClientsNotReady` → 异步加载完成 → `OnServerSceneChanged` 排空 pending、逐个 `OnRoomServerCreateGamePlayer` → `OnRoomServerSceneLoadedForPlayer`（搬运）→ `ReplacePlayerForConnection(conn, gamePlayer, KeepAuthority)`。**手写实现没有它**，因为根本不替换玩家（代价是身份全重置）。
- **`CheckReadyToBegin`**：仅当前场景是 RoomScene；统计带 `readyToBegin` 的人数 `>= minPlayers` → `pendingPlayers.Clear()` + `allPlayersReady=true`。
- **`ServerChangeScene(RoomScene)` 自动回房**：遍历 `roomSlots` 逐个 `ReplacePlayerForConnection(identity.connectionToClient, roomPlayer.gameObject, KeepAuthority)` + `readyToBegin=false` + `allPlayersReady=false`。
- **`NetworkRoomPlayer.Start` 的 `DontDestroyOnLoad`**：房间玩家跨场景存活；**游戏玩家绝不能 DDOL**（要随 GameplayScene 卸载销毁）。两个 prefab 必须分开。
- **`NetworkRoomManager.OnGUI`**（`showRoomGUI=true` 时在 GameplayScene 画 "Return to Room" 按钮）：与 `PcRoomHud` 重复，置 `showRoomGUI=false`。

## 1.4 迁移目标类结构

```
NetworkManager (Mirror 核心)
└─ NetworkRoomManager (Mirror 房间：roomSlots/pendingPlayers/OnRoom*/ReplacePlayer)
   └─ SocketRoomManager : NetworkRoomManager   【改造，替代 SocketNetworkManager】
        ├─ 字段：config、roomStatePrefab、roomChatPrefab
        ├─ 派生 API：RoomName / ConnectedPlayerCount(=roomSlots.Count) / CurrentPhase(场景派生) / Config
        ├─ [Server] TryStartGame / ServerReturnToLobby / ApplyPort
        └─ override OnRoom*（见 1.2）
   （绝不 override 那 8 个入口）

NetworkBehaviour
├─ NetworkRoomPlayer (Mirror：readyToBegin/index + CmdChangeReadyState + DDOL)
│  └─ SocketRoomPlayer : NetworkRoomPlayer   【新增】
│       ├─ [SyncVar] displayName / displayColor / isLeader / phase
│       ├─ CmdSetDisplayName / CmdRequestStartGame / CmdRequestReturnToLobby
│       └─ override: OnClientEnterRoom / OnClientExitRoom / ReadyStateChanged / IndexChanged
│
├─ NetworkPlayer  【改造为"游戏玩家"行为类，保留类名减少调用面破坏】
│       ├─ 移动（server-authoritative FixedUpdate + CmdSetInput + CharacterController）
│       ├─ 交互转发 + OnStopServer 释放
│       ├─ 新增 [Server] SetIdentity(name, color, isLeader) 供替换时搬运
│       └─ 删除 ready/phase/CmdRequestStartGame/CmdRequestReturnToLobby（迁到 SocketRoomPlayer）
│
└─ NetworkRoomState / NetworkRoomChat  【保留，改为 DontDestroyOnLoad 生成】

Prefab（重建生成器）：
  RoomPlayer.prefab = NetworkIdentity + SocketRoomPlayer
  Player.prefab     = NetworkIdentity + NetworkPlayer + LocalPlayerInput + NetworkTransformUnreliable + CharacterController
```

**关键点**：
- `Awake` 里必须先填 `RoomScene`/`GameplayScene`（`NetworkRoomManager.OnStartServer` 校验非空）；`onlineScene = config.lobbyScene` 让 host 启动自动落在房间。`onlineScene == RoomScene`（官方做法）。
- **`LocalPlayerInput`/`NetworkTransformUnreliable` 不丢的硬理由**：`NetworkTransformUnreliable` 默认 `syncDirection=ClientToServer` 要求对象持有 authority；`ReplacePlayerForConnection(..., KeepAuthority)` 保留 authority（`isOwned=true`），所以替换后移动照常工作。**必须选 `KeepAuthority`**。
- `RoomOperations.GetLocalPlayer` 在大厅拿的是房间玩家、在对局拿的是游戏玩家——Start/Return 命令要走 `SocketRoomPlayer`。

## 1.5 MultiplayerConfig 场景字段

- 现状：纯 `string` 存**全路径**（`MultiplayerConfig.cs:25-27`）。
- **结论：不必改存名字**。`Utils.IsSceneActive` 和 `SceneManager.LoadSceneAsync` 都接受全路径，`RoomScene = config.lobbyScene` 直接成立。
- 建议加 `[Scene]` 属性（Mirror `Core/Attributes.cs` + `SceneDrawer`，存的就是 `AssetDatabase.GetAssetPath`=全路径）获得下拉选择；`MultiplayerConfigEditor` 用 `PropertyField` 自动走 `SceneDrawer`，**无需改代码**，只建议在 `DrawValidation` 加 Build Settings 校验提示。

## 2.1 端口丢失 bug（验证结论 + 修复）

> **结论：唯一丢失点在 `SocketRoomDiscovery.cs:88` 的 `address = uri.Host`**——`RoomInfo` 只带 Host 不带 Port。广播链路本身的端口是对的（逐条验证过：`ServerUri()` 返回 KCP 监听端口；`NetworkDiscoveryBase` 回包原样携带该 uri；客户端 `ProcessResponse:83` 只替换 Host 保留 Port）。而 `KcpClient.Connect`/`ResolveHostname` 不解析地址串里的端口，直接用 transport 的 `Port` 字段（默认 7777），服务器配了非 7777 端口（`config.port` 可配、`NetworkStartup` 支持 `-port`）时必然连不上。

修复：

{
    public long serverId;
    public Guid roomId;          // M2 用；M1 可 Guid.Empty

    public RoomPhase phase;

// ProcessResponse 内：
port = (ushort)uri.Port,

## 2.2 多房间方案（验证结论 + 推荐）

### 方案对比

| 维度 | Match + 单场景（官方 MultipleMatches） | Scene + 加法场景（Sean-Zeo） |
|---|---|---|

### 推荐：方案 a（MatchInterestManagement + 单一物理场景）

目标：把 `Game.unity` 内容（地板 + 8 出生点 + 3 交互物，`MultiplayerDemoInitializer.cs:177-190`）做成 **`RoomEnvironment` 预制体**（全部带 `NetworkMatch`），房主 Start 时 `SocketRoomManager` 为房间 spawn 一份，`matchId = roomId`，房间 phase→InGame（房间级 SyncVar）。等待中的玩家/大厅对象统一用约定的 **`LobbyMatchId`（常量 Guid）** 实现"大厅共享、入房即隔离"。

## 2.3 发现协议设计（多房间广播该报什么）

**推荐：Response 直接带房间数组**（单条 datagram 携带 N 个房间元数据），广播同时承担"服务器心跳 + 房间列表"双重职责——房间列表 UI 需要"未连接前就能看到房间"。LAN 场景房间数少，每条 Response 几十字节，放得下。

```csharp
public struct Response : NetworkMessage
{
    public long serverId;
    public ushort port;            // KCP 服务器监听端口（transport.ServerUri().Port）
    public RoomInfo[] rooms;       // 可为空数组（服务器活着但没房）
    public IPEndPoint EndPoint { get; set; }
}
```

- 服务器无房间也照发（让客户端知道"这台服务器活着、可建房"）。
- **连接即 Join 的两段式**：列表 UI 的 Join = ① `ApplyPort(response.port)` + `StartClient(response.EndPoint.Address)`；② 连接/认证/玩家 spawn 完成后发 `ServerRoomMessage { Join, matchId = roomId }`。广播只负责发现服务器，入房是 Mirror 消息。
- 补充路径：连接后再拉一次 `ClientMatchMessage.List`（官方做法），避免广播滞后。

## 3.4 认证补强

**结论：Authenticator 不能"组件堆叠"串联**——`NetworkManager.authenticator` 是单一字段，同物体挂两个认证器时后添加者顶掉先添加者（`NetworkAuthenticator.Reset` 自动覆盖）。唯一叠用机制是**组合**：`TimeoutAuthenticator` 有 `public NetworkAuthenticator authenticator` 字段（`TimeoutAuthenticator.cs:13`），在 Awake 里转发内层认证器事件并套超时协程。

- `TimeoutAuthenticator`：解决**防挂死**（客户端连上不认证占连接数，可配合 maxConnections 刷满）。`timeout=0` 关闭。
- `BasicAuthenticator`：密码校验但**不写 `connection.authenticationData`**——框架 `NetworkPlayer.OnStartServer` 依赖 `authenticationData` 当 displayName（`NetworkPlayer.cs:29-31`），无数据回落 "Player {netId}"。
- **推荐方案甲（改动最小且保留名字）**：在现有 `SocketAuthenticator : NetworkAuthenticator` 上增加密码/Token 校验和认证超时：先校验凭据，再执行玩家名称唯一性和 `conn.authenticationData = authUsername`。`NetworkPlayer` displayName 逻辑零改动。
- 方案乙（零新代码但掉名字）：`TimeoutAuthenticator.authenticator = BasicAuthenticator`，username 当房间密码——displayName 全回落 "Player {netId}"，不推荐。
- **配置**：Bootstrap 加 `TimeoutAuthenticator`（`authenticator` 字段指向内层认证器），NetworkManager.authenticator 手动设为 TimeoutAuthenticator（注意 Reset() 顶掉，改完检查）；`timeout=30`；`NetworkStartup` 支持 `-password`。
- **风险**：密码明文跑在认证消息里（挡误入、挡不住抓包，真安全需 TLS——`Assets/Mirror/Transports/Encryption/` 已备）；`playerNames` 是 static HashSet 跨场景要清理。
